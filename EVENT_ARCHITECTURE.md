# Events and failure recovery

The application uses database transactions plus an outbox and at-least-once Kafka delivery. It does not claim end-to-end exactly-once processing.

Existing appointment events use schemaVersion 1 with eventId, appointmentId, patientId, doctorId, eventType and timestamp. The 2.0 domain envelope carries schemaVersion, eventId, aggregateId/type, eventType, patientId, providerId, correlationId and timestamp. Only identifiers and workflow states travel in these payloads; clinical reason, goals and results remain in protected records. Topics: `appointment-events`, `notification-events`, `care-events`, with `.DLT` topics for consumed inputs. Topic replication is one for local development; production requires a broker topology and replication policy appropriate to the deployment.

The existing publisher locks due rows with SKIP LOCKED and waits for broker acknowledgement. A crash after publish but before the database commit can produce a duplicate. Publication retries use bounded exponential backoff and park after twelve failures. An administrator can retry parked rows through the existing outbox API. Never delete pending events as a recovery technique.

Notification and recovery consumers have **independent Kafka groups** so each sees every appointment event. Each transactional consumer writes a durable `(event_id, consumer_name)` inbox key before business effects. Failed database work rolls the inbox key back too. Malformed inputs retry three times and then go to the source topic's DLT; failed DLT publication remains retryable. Two groups can produce two DLT records for the same malformed input, distinguished by Kafka exception/original-group headers.

Recovery locks the doctor, rechecks current cancellation and slot availability, selects up to five eligible waiting entries ordered by configured priority and registration time, and records offers plus outbox events transactionally. Offer notifications are persisted in the same transaction according to the patient's in-app preference. Offers expire after fifteen minutes or at the slot start, whichever comes first. Acceptance locks the doctor and offer, validates the active waiting entry, calls the ordinary booking service, invalidates overlapping competing offers and removes the accepted entry. A patient-scoped UUID idempotency key returns the same appointment on a successful retry. No Redis lock is required for correctness.

Care-gap detection runs only explicit database rules. It uses a transaction-scoped PostgreSQL advisory lock per scan, entity locks and a unique `(rule, rule_version, entity)` alert key. Each rule processes up to 100 matches per scan, excluding currently open alerts. A resolved alert reopens under the same identity when its condition recurs, with fresh audit, event and notification records. These writes are atomic. On failure the transaction rolls back and the next scheduled run retries. Completing/cancelling an activity resolves its open alerts in the clinical transaction. Rules are disabled or revised explicitly; there is no autonomous diagnosis or invented follow-up recommendation.

Appointment schema version 1 also accepts an optional correlationId. Older retained events without it remain readable; consumers use the event ID as a safe fallback. Cancellation, rejection and rescheduling reconcile linked scheduled referrals back to ACCEPTED, remove the obsolete appointment link and record system history once per processed event. Gap scanning can then reopen an unscheduled-referral alert. Scheduled jobs use three threads so publisher retry delays do not block expiry and gap scans.

Operational checks: inspect outbox status/retry counts, consumer lag and DLT records; restore failed dependencies before replaying. Replay retains the original event ID. Do not log payloads or expose Kafka UI publicly. Hosted broker TLS/authentication, ACLs, retention, replay permissions and backup/recovery drills remain deployment verification gates.

Care mutations emit domain envelopes in the same transaction as clinical changes/history. The `carebridge-care-notifications-v1` group validates the envelope and entity references, deduplicates durably, and records notices for the patient, responsible provider and current referral receiver. Recovery/gap notices are already persisted by their producers according to notification policy, so the care consumer does not duplicate them. Patient registration emits an identifier-only event. The unified journey includes care mutation history, retained appointment outbox events and the requesting user's delivered notifications. Original appointment history predating retained outbox data cannot be reconstructed after retention; define retention before production.
